§ 01

Introduction

1.1 Purpose

This document specifies the system and software requirements for the Mission Computer (MC) of the Swarm Search Drone. It defines the functional behaviour, external interfaces, performance bounds, safety constraints, and software architecture that the MC must satisfy to operate as a cooperative member of an autonomous search swarm.

This specification is the primary contractual baseline between the system architecture, software development, and integration teams. All MC software releases shall be traceable to requirements in this document.

1.2 Scope

Requirements apply to:

  • Onboard functional behaviour of a single drone within a swarm group during all mission phases
  • Interfaces between the MC and: the Flight Control Computer (FCC), Ground Control Station (GCS), swarm peer MCs, and the onboard IP camera
  • Software architecture, deployment packaging, and validation approach

Out of scope: GCS software, FCC firmware (PX4), MANET radio firmware, airframe design, and battery management electronics.

§ 02

System Overview

2.1 System Description

The MC is an onboard compute node that bridges the gap between the FCC (which controls the airframe) and the swarm coordination, mission execution, and AI perception tasks that require a general-purpose compute platform. It runs on a Jetson Orin NX 16GB paired with a Pixhawk 6X on a Holybro Pixhawk Jetson Baseboard.

The overarching system goal is a GNSS-denied-capable autonomous drone that can operate as a cooperative member of an autonomous search swarm, transitioning from GCS-directed setup during ingress to fully autonomous, onboard mission execution over the search area.

2.4 MAVLink Channel Separation

Important The MC operates two independent MAVLink channels. Commingling traffic on these channels is a defect.
  • GCS → FCC: Standard PX4 MAVLink 2/UDP autopilot channel. MC does not inject traffic on this channel.
  • GCS → MC: Separate MAVLink 2/UDP channel for mission upload and MC telemetry. Routed via mavlink-router on the MC.
  • MC ↔ FCC: uXRCE-DDS over ttyTHS1 serial (primary) or 192.168.12.x ethernet (secondary). Not MAVLink.

2.5 Mission Phases

PREFLIGHTPre-Flight & Mission Upload
GCS uploads mission data (waypoints, formation offsets, search polygon, swarm manifest). MC performs self-test, peer discovery, and readiness verification.
ARMING / TAKEOFFArm and Takeoff
GCS authorises arm. MC arms FCC, commands takeoff to assigned altitude, confirms position hold.
INGRESSFormation Ingress
Drone transits to the operation area in straight-and-level cruise, maintaining its assigned formation offset relative to the formation leader. GCS retains authority throughout.
MUSTERMuster at Operation Area
All drones converge on the muster point. MC reports arrival and waits for swarm quorum before proceeding.
ISR_SELECTIONISR Subnet Selection
Distributed election of which drones will perform ISR duty, based on sensor capability, battery state, and position. Fully onboard, no GCS intervention required.
VORONOI_PARTITIONVoronoi Decomposition
Participating drones exchange positions and run consensus-based Voronoi decomposition of the search area. Each drone accepts its assigned cell boundary.
SEARCHAutonomous Search Execution
Each drone executes a boustrophedon coverage path within its Voronoi cell. AI inference runs on camera feed. Detections reported to GCS in real-time.
RETURN / LANDReturn and Land
On completion of search or GCS command, drone returns to home point and lands. MC disarms FCC after landing confirmation.
§ 03

Stakeholders and User Needs

3.1 Mission Operator (GCS)

Plans and uploads missions, monitors all drones, and can reassert authority at any time. Needs: reliable telemetry, timely detection reports, simple command/acknowledge interface, and confidence that autonomous operations will not exceed the planned search boundary.

3.2 Swarm System

The collective behaviour of all MCs. Needs: consistent message formats, deterministic consensus outcomes, and graceful handling of peer loss without mission collapse.

3.3 System Integrators and Developers

Build, integrate, and validate the MC software stack. Need: containerised deployment for reproducibility, idempotent installation scripts, SITL support for test without hardware, and clear interface contracts between nodes.

§ 04

System Requirements

4.1 Functional Requirements

Each card: ID · Priority (MUST/SHOULD/MAY) · Verification method (Test / Inspection / Analysis / Demo)

4.1.1 — Mission Phase Management

FR·001MUSTAnalysis

The MC shall implement a persistent mission phase state machine with the following named states: PREFLIGHT, ARMING, TAKEOFF, INGRESS, MUSTER, ISR_SELECTION, VORONOI_PARTITION, SEARCH, RETURN, LAND, FAULT.

FR·002MUSTTest

The MC shall transition between mission phases only upon receipt of a valid GCS phase-transition command or upon satisfaction of defined autonomous transition conditions. Undefined transitions shall be rejected and reported to the GCS.

FR·003MUSTTest

The GCS shall be able to command a mission phase transition at any point during flight. The MC shall execute the command within 500 ms of receipt.

FR·004MUSTTest

The MC shall broadcast its current mission phase to all swarm peers at ≥ 1 Hz as part of the swarm heartbeat message.

FR·005SHOULDInspection

The MC shall log all mission phase transitions with timestamp, source (GCS or autonomous), and the triggering condition or event. Logs shall survive container restart.

4.1.2 — FCC Control and Monitoring

FR·010MUSTTest

The MC shall arm the FCC only after receiving explicit GCS ARM authorisation as part of the current mission upload, and only after verifying that all MC pre-arm checks pass.

FR·011MUSTTest

The MC shall command FCC disarm immediately upon receipt of a GCS DISARM command or upon triggering of a safety failsafe condition defined in §4.4.

FR·012MUSTTest

The MC shall command FCC flight mode changes (HOLD, RTL, OFFBOARD, MISSION, TAKEOFF) via uXRCE-DDS vehicle_command topic using the PX4 v1.14 command set.

FR·013MUSTTest

The MC shall upload waypoints to the FCC for autonomous execution during INGRESS and MUSTER phases via the PX4 mission upload mechanism.

FR·014MUSTTest

The MC shall subscribe to and process FCC telemetry at ≥ 10 Hz: vehicle local position, vehicle global position, vehicle velocity, vehicle attitude, armed state, flight mode, battery voltage, and battery remaining percentage.

FR·015MUSTTest

The MC shall detect FCC communication loss (silence > 1 s on the uXRCE-DDS bridge), declare a critical fault, attempt to command HOLD if the link recovers within 3 s, and notify the GCS.

FR·016MUSTInspection

The MC shall use the FccBackend abstraction layer for all FCC interactions. The underlying transport (uXRCE-DDS or MAVLink UDP) shall be configurable at deployment time without modification to application code.

4.1.3 — Formation Keeping

FR·020MUSTTest

During the INGRESS phase, the MC shall maintain its assigned formation offset (North, East, Down in metres) relative to the formation leader, commanding the FCC in OFFBOARD mode.

FR·021MUSTDemo

Formation offsets for each drone shall be uploaded by the GCS as part of the pre-flight mission upload and stored persistently on the MC across restarts.

FR·022MUSTTest

The MC shall receive the formation leader's position and velocity from swarm peer messages at ≥ 5 Hz and compute NED position setpoints accordingly.

FR·023MUSTTest

Position setpoints for formation keeping shall be published to the FCC (trajectory_setpoint topic) at ≥ 5 Hz while in OFFBOARD mode.

FR·024MUSTTest

If the formation leader's state message is not received for > 2 s, the MC shall command FCC HOLD mode and alert the GCS with the reason.

FR·025SHOULDTest

The formation controller shall implement a proportional–derivative (PD) position controller with configurable gains for NED position error. Gains shall be tunable via a ROS 2 parameter file without code recompilation.

4.1.4 — Swarm Coordination

FR·030MUSTTest

The MC shall discover and establish communication with all swarm peers listed in the uploaded swarm manifest within 30 s of entering PREFLIGHT state.

FR·031MUSTTest

The MC shall broadcast a swarm heartbeat at 1 Hz containing: drone ID, IP address, current mission phase, geodetic position, battery remaining (%), and a set of sensor health flags.

FR·032MUSTTest

A swarm peer shall be declared LOST after 3 consecutive missed heartbeats (3 s at 1 Hz). The GCS shall be notified immediately upon peer loss declaration.

FR·033MUSTTest

The MC shall participate in a distributed ISR subnet selection algorithm during ISR_SELECTION phase. The algorithm shall elect a subset of drones for ISR duty based on sensor capability flags, battery remaining, and proximity to the search area centroid.

FR·034MUSTTest

The MC shall participate in consensus-based Voronoi decomposition during VORONOI_PARTITION phase. All participating drones shall converge on a consistent, non-overlapping partition of the uploaded search area polygon within 10 s of phase entry.

FR·035MUSTTest

Upon consensus convergence, the MC shall store the boundaries of its assigned Voronoi cell and confirm acceptance to all peers before the SEARCH phase begins.

FR·036SHOULDTest

If a peer drone is declared LOST during SEARCH phase, the remaining drones shall re-run Voronoi partitioning to redistribute the lost drone's uncovered cell among active drones.

4.1.5 — Search Execution

FR·040MUSTTest

The MC shall compute a boustrophedon (lawnmower) coverage path within its assigned Voronoi cell. Path row spacing shall be parameterised by sensor footprint width and configurable overlap percentage.

FR·041MUSTTest

The MC shall upload the computed coverage path as a waypoint mission to the FCC and command autonomous mission execution for SEARCH phase transit.

FR·042MUSTTest

During SEARCH phase, the MC shall continuously process camera frames through the onboard AI inference model for target detection.

FR·043MUSTTest

All detections shall be reported to the GCS within 1 s of detection event, including: detection class label, geodetic position estimate (latitude, longitude, altitude), UTC timestamp, and confidence score (0.0–1.0).

FR·044MUSTDemo

Detection processing and GCS reporting shall not interrupt or pause coverage path execution. Both shall run concurrently.

FR·045SHOULDTest

If the assigned cell boundary is updated (e.g., following peer loss re-partitioning), the MC shall recompute and re-upload the coverage path, resuming from the nearest waypoint to the drone's current position.

FR·046MUSTTest

The MC shall transition to RETURN phase upon completion of all coverage path waypoints or upon receipt of a GCS end-mission command.

4.1.6 — Visual Localisation

FR·050MUSTTest

The MC shall provide continuous position estimates via visual odometry when GNSS fix quality falls below a configurable threshold (default: GNSS fix type < 3D fix, or HDOP > 2.0).

FR·051MUSTTest

Visual odometry pose estimates shall be fused with FCC IMU data to produce a 6-DoF pose estimate, published on /mc/local_pose at ≥ 10 Hz, and fed back to the FCC for navigation.

FR·052MUSTTest

The MC shall notify the GCS whenever localisation mode transitions between GNSS-primary and visual-odometry-primary, with the reason for the transition.

FR·053SHOULDTest

Position drift during purely visual-odometry-based operation shall not exceed 5 m/min under nominal flight conditions (no aggressive manoeuvres, adequate texture).

4.1.7 — GCS Communication

FR·060MUSTTest

The MC shall receive and persistently store mission data uploaded by the GCS: ingress waypoints, formation offset table, search area polygon (geodetic vertices), and swarm manifest (drone IDs and IPs).

FR·061MUSTTest

The MC shall acknowledge every GCS command with a success or failure response within 500 ms, including a reason code on failure.

FR·062MUSTTest

The MC shall stream a status telemetry message to the GCS at ≥ 2 Hz containing: geodetic position, heading, groundspeed, altitude, mission phase, localisation mode, battery remaining (%), and bitmask of active faults.

FR·063MUSTTest

Target detection reports shall be streamed to the GCS as they are generated (event-driven), independently of the periodic telemetry stream.

FR·064MUSTInspection

All GCS communication shall use the dedicated MC↔GCS MAVLink channel. MC software shall not inject traffic onto the FCC autopilot MAVLink channel.

4.1.8 — Health Monitoring and Failsafe

FR·070MUSTTest

The MC shall continuously monitor: CPU utilisation, memory usage, disk space remaining, GPU temperature, and the liveness of all critical ROS 2 nodes.

FR·071MUSTTest

The health monitor shall publish a /mc/health message at ≥ 1 Hz containing resource metrics and a bitmask of active health flags, and stream it to the GCS.

FR·072MUSTTest

The MC shall command FCC RTL when battery remaining falls below the configurable LOW_BATTERY_THRESHOLD (default: 20%), unless an active GCS override is in effect.

FR·073MUSTTest

The MC shall command FCC HOLD if the GCS link is lost for > 10 s while the drone is in an autonomous mission phase (INGRESS, SEARCH, or later).

FR·074MUSTTest

A watchdog shall monitor the mission_executor_node heartbeat. If no heartbeat is received for > 5 s, the watchdog shall trigger a node restart via systemd and notify the GCS.

FR·075MUSTTest

After 3 consecutive failed restart attempts on any critical node, the health monitor shall declare a critical fault and command FCC RTL via the FccBackend.

FR·076MUSTInspection

All commands issued to the FCC shall be logged to a persistent store with: UTC timestamp, command type, parameters, commanding source (GCS / autonomous / watchdog), and FCC acknowledgement result.

4.2 Interface Requirements

4.2.1 — MC ↔ FCC

IR·001MUSTTest

The MC shall communicate with the FCC via uXRCE-DDS over ttyTHS1 serial (primary) or the 192.168.12.x ethernet link (secondary). The active transport shall be indicated in /mc/health.

IR·002MUSTInspection

Transport selection (serial vs. ethernet) shall be controlled by a deployment-time configuration parameter. Switching transport shall not require code changes or recompilation.

IR·003MUSTInspection

The FccBackend interface shall expose the following ROS 2 abstraction: subscribed topics for vehicle state (position, velocity, attitude, status, battery) and published topics for commands (trajectory_setpoint, vehicle_command, offboard_control_mode). All application code shall interact with the FccBackend interface, not directly with transport-layer topics.

IR·004MUSTInspection

The MC shall subscribe to the following PX4 uORB topics via uXRCE-DDS: vehicle_local_position, vehicle_global_position, vehicle_status, battery_status, vehicle_attitude, vehicle_odometry, sensor_combined.

IR·005MUSTInspection

The MC shall publish to the following PX4 uORB topics via uXRCE-DDS: trajectory_setpoint, vehicle_command, offboard_control_mode.

IR·006MUSTTest

End-to-end command latency from MC publishing vehicle_command to PX4 actuation confirmation shall be ≤ 100 ms.

4.2.2 — MC ↔ GCS

IR·010MUSTInspection

The MC shall maintain a dedicated MAVLink 2/UDP channel to the GCS at 192.168.10.10, separate from the FCC autopilot channel. This channel is the sole path for GCS↔MC command and telemetry.

IR·011MUSTTest

The MC shall transmit a MAVLink HEARTBEAT message at 1 Hz on the GCS channel, with system_id set to the drone's assigned ID and component_id = MAV_COMP_ID_ONBOARD_COMPUTER.

IR·012MUSTInspection

All MAVLink traffic on the GCS channel shall be routed through mavlink-router v4. mavlink-router shall be the sole point of ingress and egress for this channel.

IR·013MUSTInspection

Swarm mission upload messages (waypoints, formation offsets, search polygon, swarm manifest) shall use the MAVLink COMMAND_LONG or mission item protocol. Custom payload encoding shall be documented in the ICD.

IR·014SHOULDInspection

MAVROS shall be used for GCS-facing MAVLink services where a native MAVROS interface exists (e.g., SET_MODE, COMMAND_LONG). Custom messages shall use a thin MAVLink wrapper node.

4.2.3 — MC ↔ Swarm Peers

IR·020MUSTTest

The MC shall communicate with peer drones over the MANET mesh datalink using UDP on the 192.168.10.x subnet. Peer IPs shall be sourced from the swarm manifest uploaded by the GCS.

IR·021MUSTInspection

All swarm coordination messages shall use a versioned binary protocol with a fixed header containing: protocol version (uint8), sender drone ID (uint8), message type (uint8), sequence number (uint16), and UTC timestamp (uint64, microseconds).

IR·022MUSTTest

The swarm coordination layer shall tolerate peer message latency up to 500 ms without treating the peer as LOST.

IR·023MUSTTest

Peer LOST shall be declared after 3 consecutive missed heartbeats at the nominal 1 Hz heartbeat rate (i.e., > 3 s silence).

4.2.4 — MC ↔ Camera

IR·030MUSTTest

The MC shall ingest frames from the IMX219 CSI camera via the gscam2 ROS 2 node.

IR·031MUSTTest

The camera node shall publish /camera/image_raw and /camera/camera_info at ≥ 15 FPS during SEARCH and INGRESS phases.

IR·032MUSTTest

The visual_localisation_node shall subscribe to /camera/image_raw and the IMU topic bridged from the FCC via uXRCE-DDS.

IR·033SHOULDInspection

Camera calibration parameters (intrinsics, distortion model) shall be stored in a calibration file on the MC and loaded at node startup. The camera_info topic shall reflect the loaded calibration.

4.3 Performance Requirements

PR·001MUSTTest

Mission state machine update rate: ≥ 10 Hz.

PR·002MUSTTest

Formation position setpoints published to FCC: ≥ 5 Hz during INGRESS.

PR·003MUSTTest

GCS status telemetry stream rate: ≥ 2 Hz.

PR·004MUSTTest

FCC telemetry receive and process rate: ≥ 10 Hz.

PR·005MUSTTest

Swarm heartbeat transmit rate: 1 Hz. Peer loss declared after 3 s silence.

PR·006MUSTTest

Camera frame delivery to detection pipeline: ≥ 15 FPS during SEARCH phase.

PR·007MUSTTest

Detection pipeline end-to-end latency (frame ingestion to /mc/detections publish): ≤ 500 ms.

PR·008MUSTTest

Coverage path computation for a Voronoi cell of up to 1 km²: ≤ 5 s.

PR·009MUSTTest

All MC services shall reach operational state (all containers up, DDS peers discovered, FCC telemetry flowing) within 120 s of drone-mc.target activation.

PR·010SHOULDTest

AI inference shall consume ≤ 80% of available GPU resources, preserving ≥ 20% for visual odometry and system overhead.

PR·011SHOULDTest

Visual odometry pose estimates shall be published at ≥ 10 Hz.

4.4 Safety Requirements

SFR·001MUSTTest

The MC shall not command FCC ARM without explicit GCS ARM authorisation present in the current uploaded mission. Pre-arm without authorisation shall be logged and rejected.

SFR·002MUSTTest

The MC shall not disable, suppress, or override any PX4 failsafe configuration. All MC-commanded actions shall remain within the safety envelope defined by the PX4 v1.14 failsafe configuration.

SFR·003MUSTTest

The mission_executor_node watchdog shall trigger FCC HOLD and notify the GCS if the executor's heartbeat topic is silent for > 5 s.

SFR·004MUSTTest

After 3 consecutive failed systemd restart attempts on any node declared critical, the health monitor shall issue FCC RTL via the FccBackend and set mission phase to FAULT.

SFR·005MUSTInspection

The MC shall validate the schema and parameter ranges of all incoming MAVLink messages and swarm protocol messages before acting on their content. Malformed messages shall be discarded and logged.

SFR·006MUSTInspection

All commands issued to the FCC shall be logged with: UTC timestamp, command type, parameters, commanding source (GCS / autonomous executor / watchdog / health monitor), and FCC acknowledgement result. Logs shall persist across container restart.

SFR·007MUSTTest

The MC shall command FCC HOLD if the GCS datalink is lost for > 10 s while in any autonomous phase (INGRESS, MUSTER, ISR_SELECTION, VORONOI_PARTITION, SEARCH).

SFR·008MUSTTest

The MC shall command FCC RTL when battery remaining falls below LOW_BATTERY_THRESHOLD (default: 20%). This shall not be suppressible unless a GCS override command is active and the GCS link is healthy.

§ 05

Software Requirements

5.1 Architecture

SW·001MUSTInspection

All MC software components shall be packaged as Docker containers managed by Docker Engine on the Jetson Orin NX.

SW·002MUSTInspection

All containers shall be orchestrated under the drone-mc.target systemd target. Bringing up drone-mc.target shall start all MC services in correct dependency order.

SW·003MUSTInspection

All ROS 2 nodes shall use CycloneDDS as the DDS middleware. The CycloneDDS configuration (network interface, discovery peers) shall be managed via a shared cyclonedds.xml mounted into each container.

SW·004MUSTInspection

All ROS 2 packages shall be built in a shared colcon workspace. The built workspace shall be bind-mounted into all containers that require it, avoiding redundant builds per container.

SW·005MUSTInspection

All installation and configuration scripts shall be numbered sequentially (e.g., 06-, 07-, 08-), written to be idempotent, and guarded with set -euo pipefail.

SW·006MUSTInspection

A companion smoke-test script (e.g., 06b-smoke-test-*.sh) shall exist for each installation script. Smoke tests shall emit explicit PASS / FAIL for each check, with non-zero exit on any failure.

SW·007MUSTInspection

Application-layer code shall be written in C++17. GCS-side utilities (test, monitor, log, simulation) shall be written in Python 3. Mixed-language packages shall declare their build dependencies explicitly in the colcon package manifest.

5.4 Systemd Integration

SW·040MUSTInspection

Each Docker container shall have a corresponding systemd service unit file. All service units shall declare Requires= and After= dependencies to enforce startup order.

SW·041MUSTInspection

All MC service units shall be grouped under drone-mc.target. Starting drone-mc.target shall bring up all MC services. Stopping it shall cleanly shut down all containers.

SW·042MUSTInspection

Service units shall declare resource limits: DeviceAllow (where hardware access is needed), MemoryMax, CPUQuota, PrivateTmp=yes, ProtectSystem=strict.

SW·043MUSTInspection

cgroups v2 slices shall partition resources: rt.slice for real-time services (fcc-bridge, swarm-coord), be.slice for best-effort services (logging, telemetry archival).

5.5 SITL Validation

SW·050MUSTTest

All ROS 2 nodes shall be validated against PX4 SITL (Gazebo or jMAVSim) before hardware-in-the-loop testing commences on physical drones.

SW·051MUSTTest

SITL validation shall exercise all mission phases end-to-end with a minimum two-drone simulated swarm, verifying peer discovery, formation keeping, Voronoi partition, and search execution.

SW·052MUSTInspection

All MC software components shall support a SIMULATION_MODE deployment flag. When set, hardware interfaces (uXRCE-DDS serial, CSI camera) shall be replaced with SITL-compatible equivalents without code branching in application logic.

§ 06

Constraints and Assumptions

6.1 Platform Constraints

  • Target platform is Jetson Orin NX 16GB, JetPack 6.2.2, Ubuntu 22.04 LTS aarch64. Requirements are validated on this platform only.
  • FCC is Pixhawk 6X running PX4 v1.14. uORB topic names, types, and MAVLink message IDs are fixed to this version. Compatibility with other PX4 versions is not required.
  • Network topology (IP addresses) is fixed as defined in §2.3 and is not configurable at runtime.
  • The MANET mesh radio is assumed to provide UDP transport with maximum link latency ≤ 500 ms and loss rate < 5% within the operating area.

6.2 Operational Assumptions

  • The swarm consists of a fixed, known set of drones defined at mission upload time. Dynamic entry of new drones mid-mission is not required.
  • GNSS-denied operation is bounded to environments with adequate visual texture for feature-based odometry. Featureless environments (open water, uniform terrain) are out of scope for visual localisation.
  • The search area polygon is convex or simply-connected (no holes). Non-convex polygons with holes are out of scope for the Voronoi decomposition algorithm.
  • The formation leader is designated at mission upload time and does not change during INGRESS phase.
  • One drone in the swarm is designated the ISR selection and Voronoi partition coordinator. Coordinator designation is specified in the swarm manifest uploaded by the GCS.

6.3 Build and Deployment Assumptions

  • PlantUML (v1.2026 compatible) is used for all architecture block diagrams.
  • Jira is used to track architectural decisions and phase completions.
  • Docker images are built on the Jetson (native aarch64) or cross-compiled and pushed to a local registry accessible from the Jetson.
